## 🔴 1. Lỗi Nghiêm Trọng (Critical Issues - Cần xử lý sớm)

### 1.1. Lỗ hổng RPC thực thi trực tiếp từ tài khoản vô danh (Public Anon Role)
- **Vị trí:** PostgreSQL Functions trong Supabase Database:
  - `public.admin_create_user(user_email, user_password, user_metadata, user_phone)`
  - `public.admin_delete_user(user_id)`
  - `public.admin_update_user(user_id, ...)`
  - `public.get_users_list()`
  - `public.get_system_config_secure(p_secret)`
- **Nguy hiểm:** Các hàm này được định nghĩa với quyền `SECURITY DEFINER` (chạy với quyền superuser) nhưng lại cho phép vai trò `anon` (khách vãng lai chưa đăng nhập) gọi trực tiếp qua REST API endpoint `/rest/v1/rpc/...`. Bất kỳ ai có anon key công khai trên frontend đều có thể gửi HTTP POST để tạo tài khoản, xóa tài khoản quản trị hoặc lấy danh sách nhân viên.
- **Phác đồ điều trị:** Thu hồi quyền `EXECUTE` của vai trò `anon` và `authenticated`, chỉ cho phép gọi thông qua service role hoặc kiểm tra `auth.role() = 'service_role'` / kiểm tra quyền admin nghiêm ngặt trong nội hàm.

### 1.2. 19 Bảng công khai chưa bật Row Level Security (RLS Disabled)
- **Vị trí:** 19 bảng trong public schema:
  - `generator_logs`, `mobile_equipment`, `equipment_transfers`, `infrastructure_projects`, `smartw_pakh`, `smartw_alarms`, `daily_work`, `power_schedule`, `datasites`, `operation_defects_logs`, `fuel_and_expenses`, `sran_5g_tracker`, `parsed_invoices`,...
- **Nguy hiểm:** Bảng không bật RLS đồng nghĩa với việc cổng API Supabase PostgREST mở cửa tự do. Người dùng có anon key có thể tự do đọc, sửa, xóa dữ liệu nhạy cảm của trạm hoặc nhật ký máy phát điện nếu biết tên bảng.
- **Phác đồ điều trị:** Bật `ALTER TABLE public.<table_name> ENABLE ROW LEVEL SECURITY;` và tạo chính sách (policies) phân quyền rõ ràng:
  - Cho phép `anon` hoặc `authenticated` SELECT dữ liệu trạm/lịch cúp điện.
  - Chỉ cho phép `authenticated` (nhân viên) INSERT/UPDATE.
  - Chỉ cho phép `admin` DELETE.

## 🟡 2. Cảnh báo (Warnings - Nên cải thiện)

### 2.1. Kích thước Bundle Frontend quá lớn (3.44 MB JS trong 1 file)
- **Vị trí:** `tvt3_v2/src/App.jsx`
- **Thực trạng:** 15 trang (bao gồm các trang cực nặng như `NetworkMap` kèm Leaflet, `Generator` kèm Recharts/Docxtemplater/ExcelJS, `Sran5gProject`) đều được import tĩnh đồng bộ (`import NetworkMap from './pages/NetworkMap'`).
- **Hậu quả:** Khi người dùng mở bất kỳ trang nào (kể cả chỉ xem VHKT RAN trên điện thoại ngoài trạm), trình duyệt phải tải nguyên gói JavaScript nặng 3.44 MB (902 KB nén), làm tốn dung lượng 4G và làm chậm tốc độ hiển thị ban đầu (FCP/LCP).
- **Phác đồ điều trị:** Áp dụng `React.lazy()` và `Suspense` cho các trang lớn trong `App.jsx`, chia nhỏ (code splitting) thành từng chunk riêng biệt.

### 2.2. Lộ token dự phòng (Fallback Token Hardcoding) trong Backend Python
- **Vị trí:**
  - `backend/bot_mll_tvt3.py` (dòng 8 & 49): Chứa token bot Telegram fallback `7899414034:AAGj...`
  - `backend/fetch_outages.py` (dòng 122) & `daily_report.py` (dòng 619): Chứa token Viber fallback `56a990b99bf464bd-...`
  - `backend/smartw_worker.py` (dòng 488-489): Hardcode `pakh_token` và `outages_token`.
- **Nguy hiểm:** Mặc dù code chạy nội bộ, việc hardcode token trong file Python có thể dẫn đến rò rỉ khi chia sẻ mã nguồn.
- **Phác đồ điều trị:** Đưa toàn bộ vào file `.env` trên server và xóa bỏ hoàn toàn các chuỗi token fallback trong code.

### 2.3. RLS Policy dựa trên `user_metadata` có thể bị leo quyền
- **Vị trí:** Bảng `system_config` (policy `admin_all_policy`)
- **Nguy hiểm:** Policy kiểm tra quyền dựa trên `auth.jwt() -> user_metadata -> role`. Người dùng thông qua API auth của Supabase có thể tự cập nhật `user_metadata` của mình thành `admin`.
- **Phác đồ điều trị:** Quản lý quyền thông qua bảng `user_roles` độc lập hoặc Supabase Custom Claims (`app_metadata`), chỉ admin hoặc backend service role mới có quyền ghi vào `app_metadata`.

### 2.4. Thiếu Index trên các khóa ngoại (Foreign Keys)
- **Vị trí:**
  - `equipment_transfers.equipment_id`
  - `fuel_and_expenses.site_id`
  - `generator_logs.site_id`
  - `operation_defects_logs.site_id`
- **Hậu quả:** Khi số lượng log máy phát và chi phí tăng lên hàng chục ngàn dòng, các truy vấn JOIN hoặc lọc theo trạm sẽ bị Table Scan, làm chậm database.
- **Phác đồ điều trị:** Tạo các index bao quát: `CREATE INDEX idx_gen_logs_site_id ON generator_logs(site_id);`
